# AlEntlaq POS

## قاعدة البيانات

يستخدم التطبيق ملف Microsoft Access بصيغة `.accdb` على جهاز Windows مركزي. تتصل محطات البيع بخدمة Next.js على الشبكة المحلية؛ لا تفتح محطات البيع ملف Access مباشرة ولا تضعه على مجلد SMB مشترك.

هذه البنية تستهدف نشرًا صغيرًا (3–5 محطات) مع اختبار تزامن فعلي قبل التشغيل. ملف Access محدود بالحجم والتزامن؛ إذا زاد عدد المحطات أو كثرت الكتابات المتزامنة، استخدم قاعدة خادمية مثل PostgreSQL أو SQL Server بدل Access.

## إعداد جهاز الخادم

المتطلبات:

- Windows 64-bit وNode.js 24 x64.
- مشغّل Microsoft Access ODBC / Access Database Engine 64-bit.
- نسخة المشروع واعتمادياته، مع السماح بتشغيل سكربت تثبيت `odbc`.
- إعداد جدار حماية Windows للسماح بالمنفذ المحدد من أجهزة الشبكة المحلية فقط. لا تعرض الخدمة مباشرة على الإنترنت؛ استخدم HTTPS عند عبور شبكة غير موثوقة.

أنشئ ملفًا جديدًا؛ يرفض السكربت استبدال ملف موجود:

```powershell
.\scripts\create-access-database.ps1 -Path 'C:\AlEntlaqPOS\Data\AlEntlaqPOS.accdb'
```

أنشئ ملف إعدادات للخادم (ولا تضعه في نسخة تطبيق محطات البيع):

```dotenv
ACCESS_DB_PATH=C:\AlEntlaqPOS\Data\AlEntlaqPOS.accdb
POS_API_TOKEN=ضع-قيمة-عشوائية-طويلة-هنا
POS_PORT=3000
```

يمكن حفظ الإعدادات في `.env.local` أو `.env` في مجلد المشروع. يجب أن يتطابق `POS_API_TOKEN` مع القيمة في إعداد كل محطة. لا تضف أسرار قاعدة البيانات إلى ملفات التوزيع.

ثبّت الاعتماديات وابنِ نسخة الخادم العادية (لا تستخدم `build:electron` على جهاز الخادم):

```powershell
pnpm install
pnpm build
```

## تشغيل الخادم ومحطات البيع

ابدأ خدمة الخادم بعد الترحيل:

```powershell
pnpm start:host
```

عند أول تشغيل، تنشئ الخدمة الجداول والفهارس والعلاقات اللازمة. لا تغيّر مسار ملف Access أثناء تشغيل الخدمة، وأنشئ النسخ الاحتياطية بعد إيقافها وإغلاق جميع المحطات.

في قاعدة جديدة، تُنشأ حسابات المستخدمين الافتراضية الناقصة فقط؛ غيّر كلمات مرورها قبل الاستخدام الفعلي.

على كل محطة، افتح ملف `server.json` الذي ينشئه التطبيق أول مرة ضمن مجلد بيانات المستخدم في Windows (عادةً `%APPDATA%\AlEntlaqPOS\server.json`) واضبطه على عنوان الخادم والرمز المشترك:

```json
{
  "serverUrl": "http://192.168.1.10:3000",
  "apiToken": "نفس-قيمة-POS_API_TOKEN-على-الخادم"
}
```

يمكن بدلًا من ذلك ضبط متغيري البيئة `POS_SERVER_URL` و`POS_API_TOKEN` للمستخدم. لا تضع ملف `.env` الخاص بالخادم في أجهزة العملاء.

أسماء البنوك والخزائن فريدة ولا يمكن تكرارها. عند ظهور رسالة بأن الاسم مسجل بالفعل، استخدم الحساب الموجود أو اختر اسمًا مختلفًا؛ إعادة المحاولة بالاسم نفسه لن تنشئ حسابًا آخر. يتطلب تحديث رسائل الأخطاء تحديث الخادم وتطبيق المحطة معًا.

زر القلم في بطاقة البنك يفتح تعديل الحساب الموجود، بما في ذلك الرصيد المعروض، دون إنشاء حساب جديد أو تغيير ارتباط سنداته. زر الإضافة ينشئ حسابًا جديدًا مستقلًا.

تُحفظ قائمة الأسعار المخصصة للعميل في نسخة سطح المكتب عبر اتصال الخادم المُعدّ في `server.json`، وفي المتصفح عبر واجهة العملاء. تُحمّل الأسعار المحفوظة مجددًا مع العميل وتُستخدم في البيع، وتُعرض رسالة السبب عند فشل الحفظ. السعر صفر صالح؛ مسح خانة السعر وحفظ القائمة يلغي تخصيص ذلك الصنف ويعيد تطبيق قواعد التسعير الافتراضية. تُحفظ القائمة كاملة في معاملة واحدة. تعرض بيانات كل صنف الاسم والكود والنوع والمقاس والدرجة واللون والمورد والطول والوزن وسعر الكيلو في صف واحد مع تمرير أفقي عند الحاجة، وتُرتب الأصناف ذات الأسعار المخصصة أعلى القائمة. يطبع زر «طباعة الأصناف المخصصة» الأصناف المسعرة للعميل وحدها مع بياناتها وأسعارها. يتطلب الإصلاح إعادة بناء تطبيق المحطة وتحديث الخادم معًا.

في تبويبي العملاء والموردين، اختيار «من / إلى» يعرض أصحاب الحركات في الفترة فقط، ويحسب البطاقات والإجماليات وطباعة الجدول من فواتير ودفعات الفترة دون أرصدة سابقة. يشمل تاريخ «إلى» اليوم كاملًا. يرث كشف الحساب الفترة المختارة مع إمكانية تعديلها داخله، وتظهر الفترة في الطباعة. «عرض الكل» يعيد العرض غير المقيّد بالفترة. لا تغيّر الفلترة الأرصدة الأصلية في نماذج تعديل البيانات.

تُطبّق الفترة والبحث معًا أيضًا على فواتير المشتريات والمصروفات العامة وسندات الصرف وسندات القبض والفواتير وعروض الأسعار. تعتمد الصفوف والإجماليات وزر «طباعة الجدول» على القائمة المفلترة نفسها، وتظهر الفترة في التقرير المطبوع. تعتمد الحركة على تاريخها المسجل، أو تاريخ إنشائها عند غيابه. تظل طباعة الفاتورة أو السند الفردي كما هي. لا تشمل الفلترة الزمنية المخزون والبنوك لأنهما يعرضان أرصدة حالية ولا يحتويان على اختيار فترة.

تظهر كشوف حساب العملاء والموردين داخل التطبيق بالشكل الداكن القديم: جدول مستقل للفواتير وجدول للسندات، مع أزرار فتح وطباعة كل مستند. يحتفظ زر «طباعة الكشف» بالتنسيق الورقي الجديد ذي الجدول الموحد والرصيد المتحرك والإجماليات. يشترك العرض والطباعة في الفترة والبيانات نفسها، وتبقى مبالغ شراء المورد للمدير فقط.

من تبويب «الخصومات» يمكن إصدار سند مستقل بمبلغ ثابت: «خصم مسموح به» للعميل أو «خصم مكتسب» من المورد. اختر الطرف وأدخل المبلغ والسبب اختياريًا؛ يُسجَّل تاريخ الخادم ورقم السند تلقائيًا، ولا يسمح بمبلغ أعلى من الرصيد المستحق وقت الحفظ. مثلًا، يخفض خصم 50 رصيدًا قدره 1000 إلى 950. تظهر السندات وإجمالي كل نوع في التبويب، وكشوف الحساب والبطاقات وتقارير الفترة، ويمكن طباعة السند أو الجدول. يرى الكاشير خصومات العملاء، وأمين المخزن خصومات الموردين، والمدير النوعين وفق صلاحيات التبويبات الحالية.

الخصم هنا تسوية رصيد وليس سند قبض أو صرف: لا يغيّر النقدية أو المخزون أو الفاتورة أو الضريبة المسجلة، ولا ينشئ قيد أستاذ عام أو يعدّل تقرير أرباح مستقلًا. استشر المحاسب بشأن المعالجة الضريبية إذا كان الخصم يستلزم تعديل فاتورة ضريبية. لا يُلغى سند الخصم المستقل أو يُعكس تلقائيًا عند المرتجع، وتؤخذ خصومات العميل في الحسبان عند حساب المبلغ المستحق رده. مثلًا، إذا كانت الفاتورة 100 دون سداد وسُجّل خصم 20، فإن إرجاعها بالكامل يجعل مبلغ الرد 20 ويتطلب اختيار وسيلة رد لإتمام المرتجع. راجع هذه المعالجة مع المحاسب قبل اعتماد المرتجع. لا توجد حاليًا وظيفة لتعديل السند أو حذفه بعد حفظه. لتفعيل الميزة على قاعدة قائمة، أوقف المحطات وخذ نسخة احتياطية، ثم حدّث الخادم وأعد تشغيله وأعد بناء المحطات؛ يُنشأ جدول الخصومات تلقائيًا.

يمكن إنشاء مرتجعات متعددة لكل فاتورة مبيعات من قائمة الفواتير. يحدد المستخدم الصنف والكمية في كل مرة، ويمنع النظام تجاوز الكمية الأصلية بعد جمع المرتجعات المعتمدة السابقة. تُحسب القيمة والضريبة من بيانات الفاتورة، وتعود الكميات إلى المخزون ضمن معاملة واحدة. تُخصم قيمة المرتجع من مديونية العميل أولًا؛ ويُرد أي فائض نقدًا أو من بنك مختار، مع إظهار المرتجع ورد المبلغ في كشف العميل، أرصدة العملاء وتقارير صافي المبيعات، وطباعة إشعار مرتجع مرتبط بالفاتورة. لا يسمح بحذف فاتورة لها مرتجعات. يتطلب التشغيل تحديث كود خادم Access وإعادة تشغيله، ثم إعادة بناء تطبيق المحطة؛ تُنشأ جداول المرتجعات الجديدة تلقائيًا دون تعديل الفواتير السابقة.

يظهر سطر «رصيد أول المدة» قبل حركات كشف العميل والمورد في المعاينة والطباعة، حتى عند اختيار فترة أو عدم وجود حركات. يعرض الرصيد الافتتاحي المحفوظ عند تأسيس الحساب، وليس الرصيد الحالي أو المتبقي، ولا يمثل رصيدًا متراكمًا محسوبًا قبل تاريخ «من». في الكشف التفصيلي، «إجمالي الفواتير والرصيد الافتتاحي» يجمع الافتتاحي مرة واحدة مع فواتير الفترة، و«إجمالي المطلوب» يطرح سدادات الفترة منه. تتطابق المعاينة والطباعة، بينما تبقى إجماليات قوائم التبويبات للفترة فقط كما سبق.

يُحفظ الرصيد الافتتاحي للمورد مستقلًا عن رصيده الحالي؛ لا تغيّره المشتريات أو الدفعات أو الخصومات. تعديل الافتتاحي يغيّر الرصيد الحالي بمقدار الفرق فقط ويحافظ على الحركات السابقة. عند تحديث الخادم، يُضاف الحقل تلقائيًا لقواعد Access القديمة وتُستخرج قيمته مرة واحدة من الرصيد الحالي ناقص جميع المشتريات زائد جميع المدفوعات والخصومات المكتسبة، دون تغيير الرصيد الحالي أو الحركات. إذا كانت الأرصدة الحالية قد عُدّلت يدويًا سابقًا، راجع القيم المستخرجة وصحّحها من بطاقة المورد. أنشئ نسخة احتياطية وأوقف المحطات قبل تحديث الخادم، ثم حدّث جميع المحطات معه.

تصميم كشوف العملاء والموردين موحّد بين المعاينة والطباعة: جدول واحد يبدأ بالرصيد الافتتاحي، ثم الفواتير والسندات بترتيب زمني تصاعدي، ثم الإجماليات كسطور في نهايته. يعرض الجدول المدين والدائن والرصيد بعد كل حركة، مع بيانات المستند والبنك والملاحظات. يمكن فتح المستند من رقمه في المعاينة، وتُخفى الأزرار في الطباعة. يستخدم التصميم ألوانًا هادئة وحدودًا أفقية رفيعة، ويكرر رأس الجدول عند تعدد الصفحات دون تكرار الإجماليات. تبقى صلاحيات عرض مبالغ فواتير الموردين كما هي.

تستخدم جميع المطبوعات قالب كشف الحساب نفسه فعليًا، بنفس الخط والألوان ورأس الجدول وسطور الإجماليات، بما فيها فواتير المبيعات وعروض الأسعار والمشتريات وسندات القبض والصرف وجداول التبويبات. تستخدم المستندات صفوفًا مضغوطة لاستيعاب مزيد من البيانات، وتعرض المعاينة عرض مساحة الطباعة الفعلي بالمليمتر. جميع المطبوعات A4 رأسي بهوامش 12 مم أعلى وأسفل و10 مم جانبيًا؛ لا يتحول أي تقرير تلقائيًا إلى الوضع الأفقي. تُلفّ بيانات الجداول العريضة داخل الأعمدة بخط أصغر دون حذف بيانات أو قصّ الأعمدة. تُعرض إجماليات الفاتورة كسطور في جدول الأصناف، مع الحفاظ على الضرائب ورمز QR والتحويل من عرض سعر، وعلى التوقيعات وكعب سند القبض والصرف. في كشف الحساب أُلغي عمود «العملية» وحُذف نوع الفاتورة وتفاصيل الضريبة من البيان؛ تبقى بيانات إذن الاستلام والمستلم والبنك والملاحظات، دون تغيير الحسابات.

تُخفى أرقام التسجيل الضريبي والسجل التجاري من جميع المطبوعات ومعايناتها، بما فيها بيانات البائع والعميل والمورد وتقرير الموردين. تُسمّى الفواتير «فاتورة» فقط دون وصفها بالضريبية أو غير الضريبية، وتبقى عروض الأسعار مميزة باسم «عرض سعر». لا يحذف ذلك البيانات المحفوظة ولا يغيّر احتساب الضرائب أو مبالغها أو رمز QR.

## التطوير

تتوفر أزرار الطي والفتح والتثبيت أعلى القائمة الرئيسية اليمنى وقائمة المبيعات والعروض اليسرى. عند طي القائمة اليمنى تبقى أيقونات التنقل ظاهرة وقابلة للنقر مع الاحتفاظ بأسمائها لقارئ الشاشة؛ تتمدد بعد بقاء المؤشر عليها ثانيتين، ويُلغى الانتظار عند المغادرة. تفتح القائمة اليسرى فور المرور فوق شريطها دون انتظار. القائمتان مثبتتان افتراضيًا؛ طي القائمة يلغي تثبيتها، وتظهر القائمة غير المثبتة فوق المحتوى دون حجز عرض وتُطوى عند مغادرة المؤشر. يمكن فتحهما بالنقر وتثبيتهما مجددًا. تتحرك القوائم خلال 300 مللي ثانية بتدرج هادئ مع احترام إعداد تقليل الحركة، دون مسح السلة أو الحقول.

عند ظهور `linkedQuotationId is not defined` أثناء إصدار فاتورة من محطة، حدّث تطبيق Electron وأعد تشغيله: النسخ القديمة قد تستخدم متغير ربط عرض السعر دون تعريفه. لا يكفي تحديث الخادم لإصلاح الكود المجمّع داخل المحطة. تُصدر الفاتورة العادية دون ربط عرض سعر؛ وعند التحويل، يُعلَّم العرض «تم التحويل» فقط بعد حفظ فاتورة فعلية ضمن المعاملة نفسها.

تعرض بطاقات الأصناف في البيع والمخزون بياناتها وسعر البيع بخط 11 بكسل والاسم بخط 14 بكسل. يظهر الكود والاسم والنوع في أعلى البطاقة فوق الصورة، وبقية المواصفات في صف واحد تحتها بمحاذاة اليمين دون عناوين مثل «اللون» و«المورد»، مع تمرير أفقي عند ضيق البطاقة دون حذف المواصفات. تظهر الاختصارات بجانب القيم: م للمقاس، ط للطول، ز للوزن، وش لسعر الشراء ون للنسبة للمستخدم الرئيسي فقط. يعرض سعر الشراء والنسبة مقربين لأقرب عدد صحيح دون تغيير القيم المحفوظة أو الحسابات، وتبقى دقة المقاسات والأطوال والأوزان وسعر البيع كما هي. تتلون خلفية خانة اللون بلون الصنف مع نص متباين؛ تبقى القيم غير اللونية مثل «مقاوم» محايدة. يظهر سعر البيع والمخزون وزر الإضافة للسلة في صف واحد مستقل أسفل التفاصيل في شاشة البيع، مع التفاف نص السعر والمخزون داخل خانتيهما عند ضيق البطاقة دون إخفاء زر السلة. تستخدم بطاقات نقطة البيع عرضًا أدنى 220 بكسل بدلًا من 230 بكسل، مع حد أقصى أربعة منتجات في الصف مهما اتسعت المساحة. تتسع أربعة منتجات عند توفر 916 بكسل مع الفواصل، ويقل عدد الأعمدة تلقائيًا في المساحات الأضيق لمنع ضغط البيانات. تبقى بطاقات المخزون بعرض أدنى 320 بكسل متى سمحت الشاشة. يستطيع المستخدم الرئيسي (ADMIN) تغيير الصورة من زر الكاميرا في البطاقة واختيار ملف JPG أو PNG أو WebP أو GIF من الكمبيوتر بحجم أقصى 2 ميجابايت. تُحفظ الصورة داخل بيانات الصنف لتظهر بعد إعادة التشغيل وعلى المحطات الأخرى، دون تغيير الأسعار أو المخزون أو المورد أو بقية المواصفات. لا يظهر زر رفع الصور لباقي المستخدمين.

بعد حفظ صنف جديد يظل نموذج الإضافة مفتوحًا وتبقى جميع الحقول كما هي؛ يمكن تغيير اللون أو المواصفات ثم الحفظ لإضافة صنف مستقل، دون التحول إلى تعديل الصنف السابق. يستمر منع تكرار الصنف بنفس المواصفات. يُعطّل زر الحفظ أثناء الطلب، وتظهر رسائل النجاح والأخطاء داخل النموذج دون نافذة تأكيد أصلية تعطل التركيز في Electron. تُحدّث قائمة الأصناف في الخلفية دون شاشة تحميل. تعديل صنف موجود يحتفظ بسلوك إغلاق النموذج بعد نجاح التعديل.

```powershell
pnpm dev
pnpm electron-dev
```

يلزم أن يكون `ACCESS_DB_PATH` و`POS_API_TOKEN` مضبوطين على الخادم المحلي، وأن يتطابق الرمز مع ملف `server.json` الخاص ببيئة التطوير. لبناء تطبيق Electron:

إذا فشلت جميع عمليات التحميل برسالة `POS server returned an invalid response (404)`، فهذا يعني أن عنوان الخادم يعيد صفحة غير موجودة بدل واجهة البيانات، وليس أن الجداول فارغة. تحقق من `serverUrl` في `server.json`، ثم أوقف `pnpm dev` وأعد تشغيله إذا كان قد ظل مفتوحًا أثناء بناء نسخة Electron بالسكربت القديم. يستبعد بناء Electron الآن ملفات واجهات البيانات ووكيلها من التصدير بالإعدادات دون نقلها أو حذفها، ولا يحذف ذاكرة خادم التطوير؛ يحفظ Next.js ملفات سطح المكتب في `out` مع إبقاء ذاكرة التطوير في `.next\dev`. أبقِ صفحات سطح المكتب بصيغة `.tsx` وواجهات البيانات والوكيل بصيغة `.ts`.

```powershell
pnpm build:electron
pnpm package
```

الإصدار السادس هو `1.6.0`. ينتج بناء Windows ملف التثبيت `dist-v6\AlEntlaqPOS Setup 1.6.0.exe`، وتوجد النسخة غير المثبتة في `dist-v6\win-unpacked`. مجلد البناء مستقل عن مجلدات الإصدارات السابقة؛ لا يستبدل بيانات Access أو إعدادات اتصال المحطات. تحديث تطبيق المحطة لا يحدّث خدمة الخادم؛ انشر كود الخادم المحدّث وأعد تشغيل خدمته لتفعيل تعديلات واجهات البيانات.
